      03 · The math of agent cost

      Every dollar on the invoice traces back to a token.

      Per callllm_cost = in_tok × price_in + (out_tok + reasoning_tok) × price_out

      Output and reasoning tokens cost 4-5× input. A cached prefix reprices at ~0.1× input.

      Per turnturn_cost = llm_cost + Σⱼ tool_costⱼ

      Every tool crossing carries its own price - a search, a write, a message.

      Per run · one agentagent_cost = Σᵢ (llm_costᵢ + action_costᵢ) for i = 1..N

      N is loop iterations. Unmanaged, growing context makes the curve worse than linear.

      Per system · multi-agentsystem_cost = Σₘ agent_costₘ for m = 1..M

      One user request, M agents delegating - M nested bills to reconcile.

      Worked example · FinSight

      Can the first call fit the budget?

      gpt-5.2-chat$2.50 in · $10.00 out per 1M tokens · output cap 4,000 (incl. reasoning) · input ≈ 233

      4,000 × $10 / 10⁶+233 × $2.50 / 10⁶

      ≈$0.0400+$0.0006=$0.0406

      $0.005 budget$0.0406 ≥ $0.005 → blocked before a single token is billed

      $0.25 budget$0.0406 < $0.25 → allowed; the ledger tracks actual spend

      Typical FinSight run: 2 LLM calls · 5 MCP tool calls · 5,585 tokens ≈ $0.022

      07 · What's missing

      Token management must govern the run, not the request.

      A gateway sees

      One request at a time

      Per-request caps, keys and routing. A great front door - but blind to the task.

      A run is

      The whole task

      Loops, growing context, fan-out, sub-agents. One cumulative bill - per run and per customer.

      • One budget across every agent in the run, on a shared ledger
      • Enforcement in the call path, before the spend lands
      • Act, don't alert - steer or halt while the run is live
